# ADR-0002: Раннер фабрики — официальный образ Hermes, поллинг, обновления из GitHub

- **Статус:** принято (2026-11-24)
- **Контекст:** задачи #11 (триггер старта), #13 (раннер фабрики), обсуждение с alex

## Контекст

Фабрике нужен постоянно работающий исполнитель: слушает доску, берёт задачу из Todo, гоняет пайплайн. Требование: развёртывание и обновление из GitHub с минимальным ручным вмешательством — один bootstrap-запуск, дальше всё потоком PR.

Открытые вопросы: как упаковать Hermes, как получать триггер с доски, как обновляться, где секреты.

## Решение

### Упаковка: официальный образ, не свой Dockerfile

Используем `nousresearch/hermes-agent` (stateless: весь стейт — в одном каталоге, монтируется с хоста). Почему не свой Dockerfile: мы не форкаем Hermes, фабрика — оркестратор над ним; обновления Hermes приходят сами через pull образа, наш код меняется отдельно через git. Смешивать два жизненных цикла в одном образе — лишняя сложность.

### Триггер: script-only поллинг, LLM по требованию (закрывает #11)

- Watchdog-скрипт (без LLM) каждые 2–3 минуты спрашивает у GitHub API: есть ли карточки в Todo на доске продукта. Пусто — выход, стоимость ноль.
- Задача нашлась — скрипт один раз запускает `hermes chat -q` с промптом продуктового цикла (Implementation → Quality Gates → Self-Review, этапы 2–4 пайплайна).
- Webhook и GitHub App отклонены для v1: требуют либо входящий порт на VPS, либо установку приложения в аккаунт; поллинг живёт за NAT, переживает ребуты и не требует ничего настраивать в GitHub. Задержка 2–3 минуты для контура разработки несущественна.

### Обновления: git pull + pull образа по хостовому cron

Каждые 5 минут на хосте (пользователь `factory`): `git pull` репозитория fabric + `docker compose pull && up -d`. Образ stateless — обновление = пересоздание контейнера без потери конфига/памяти/навыков (они в смонтированном томе). Изменения логики раннера (watchdog, промпты, compose) приезжают обычным PR в fabric → alex approve → cron раскатывает сам.

### Секреты: только на хосте

`/home/factory/.env` (не в git): ключи LLM-провайдера для Hermes, токен pfbot13 (read доски, ветки/PR — тот же токен бота). В GitHub Secrets ничего не дублируем: CI фабрики на VPS не деплоит, деплоит хостовый cron.

### Идентичность

В GitHub раннер действует как pfbot13 (#16). Ворота строгие: любое изменение кода фабрики/продукта — PR + approve alex-pf. Раннер не может смёржить свой PR сам.

## Последствия

- Bootstrap (`runner/bootstrap.sh`, один запуск под root): создать пользователя `factory`, поставить Docker, склонировать fabric, принять `.env`, поднять compose, поставить cron обновлений. Дальше ручное вмешательство не требуется.
- Развёртывание раннера ≠ закрытие v1: критерий v1 (задача в Todo → сама в реализацию) проверяется прогоном на G1.
- Модель «runner как официальный образ + наш код сбоку» переносима на новый продукт/сервер: bootstrap.sh + .env + git clone.

## Дополнение (2026-11-24): колонка Approved = решение человека

Доска G1 расширена колонками **Need Review** и **Approved** (решение alex):
- бот закончив цикл, двигает карточку в Need Review и останавливается;
- alex смотрит PR и двигает карточку в Approved — это решение «принято»;
- watchdog исполняет: squash-merge связанного PR от pfbot13, карточка в Done.

Следствие для ворот g1: approval в GitHub не требуется (ruleset 0 approvals) — review происходит на доске, merge выполняет бот по явному сигналу человека. Репозиторий фабрики (fabric) остаётся со строгими воротами: там review — в GitHub, approval 1, merge только alex-pf.

## Альтернативы

- **Свой Dockerfile поверх Hermes** — отвергнуто: два жизненных цикла в одном образе, мы начинаем сопровождать форк.
- **Webhook из GitHub** — отвергнуто для v1: входящий порт/приложение, сложность, выигрыш — минута задержки.
- **LLM-поллинг (cron с моделью каждые N минут)** — отвергнуто: деньги за каждый пустой тик; script-only watchdog бесплатен.
