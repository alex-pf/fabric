# ADR-0001: Граница ответственности фабрики и продукта — механизм vs содержимое

- **Статус:** принято (2026-11-24)
- **Контекст:** обсуждение архитектуры фабрики, тред с alex (Mattermost)

## Контекст

Фабрика (Fabric) задумана как универсальный инструмент запуска продуктов с одинаковой архитектурой, но не «мега-комбайн». Код фабрики и кода продукта разделены по репозиториям (см. журнал, день 0, решение 2). Встал вопрос: что где находится.

Исходная интуиция: (1) продукт хранит свою конфигурацию у себя, (2) фабрика настраивает инструментарий продукта — агентов, проверки, правила деплоя.

Проблема этой формулировки: проверки и правила деплоя наполовину продуктово-специфичны (конкретные команды под стек продукта, конкретные цели деплоя). Если фабрика хранит их у себя — привязывается к продукту и разрастается. Если продукт — неясно, что остаётся фабрике.

Второй вопрос: этапы вроде уточнения бизнес-требований продуктово-специфичны (вопросы аналитика разные для разных продуктов), но механика этапа (агент ↔ автор в комментариях issue, движение карточки) — универсальна.

## Решение

Разделение не «фабрика = инструментарий, продукт = конфигурация», а **механизм vs содержимое**:

- **Фабрика владеет механикой этапов пайплайна.** Этап — это универсальный раннер: вход → агент с инструкциями из конфига продукта → выход/ворота. Фабрика знает *форму* этапов, а не их содержание. Примеры: quality-gates умеет запускать команды из конфига и блокировать PR по красному; intake-clarification умеет вести диалог агента с автором задачи в комментариях issue и двигать карточку по сигналу «требования уточнены».
- **Продукт владеет содержимым.** Всё продуктово-специфичное знание живёт в репозитории продукта: команды проверок под стек, правила деплоя, правила уточнения бизнес-требований (шаблоны вопросов, примеры хорошей задачи), включённые этапы, пин версии фабрики.

Фабрика — тупой исполнитель конфига продукта. Универсальность фабрики = библиотека версионируемых этапов + исполнитель, наполняемый декларативным конфигом продукта.

### Целевая структура (ориентир, не обязательность к v1)

**Репозиторий fabric:**

```text
stages/            # механика этапов, версионируется
  intake/
  quality-gates/
  deploy/
agents/            # универсальные исполнители

```

**Репозиторий продукта:**

```text
.fabric.yaml       # включённые этапы, пин версии фабрики
.fabric/
  checks.md        # команды проверок под стек
  deploy.md        # правила деплоя
  intake.md        # правила уточнения бизнес-требований

```

### Эволюция окружения продукта (сценарий «умнеющей фабрики»)

1. Фабрика выкатывает новый этап (только механику).
2. Продукт поднимает пин версии фабрики и включает этап в `.fabric.yaml` — **opt-in, не push**: ни один продукт не обязан брать все этапы.
3. Конфига этапа у продукта нет → этап работает на generic-дефолтах, либо бот фабрики сам заводит на доске продукта техническую задачу «опишите правила» (dogfooding: дыра в конфигурации превращается в задачу на доске).

## Последствия

- Апгрейд фабрики не меняет поведение продуктов автоматически — только через пин версии + включение этапа. Защита от «мега-комбайна».
- Новый продукт = репозиторий с конфигом + доска, а не форк фабрики.
- Слой конфигурации (`.fabric.yaml`, оркестрация этапов из конфига) **не строится в v1**. В v1 конфиг захардкожен или сведён к одному файлу. Конфиг-слой вводится, когда появляется вторая фабричная фича (например, intake-clarification) или второй продукт — иначе абстракция проектируется вслепую.

## Альтернативы

- **Фабрика хранит всё, включая продуктовые проверки и промпты.** Отвергнуто: фабрика прирастает продуктовым знанием, теряет универсальность, обновление фабрики рискует ломать продукт.
- **Продукт хранит всё, фабрика — только шаблоны.** Отвергнуто: каждый продукт дублирует механику этапов, обновления пайплайна не доходят до продуктов.
