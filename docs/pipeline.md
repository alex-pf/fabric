# Пайплайн разработки фичи (Feature Delivery Pipeline)

Ядро фабрики. Каждая задача — продуктовая фича G1 или задача Fabric — проходит этот контур.
Все улучшения фабрики встраиваются в один из этапов, не ломая остальные.

## Принципы

1. **Агент делает работу, человек принимает решения.** Человеческое вмешательство — это review и приоритизация, не написание кода.
2. **Качество гарантируется воротами, а не доброй волей.** Ничто не доходит до main в обход автоматических проверок.
3. **Всё записывается.** Каждый прогон даёт данные для журнала фабрики.

## Этапы

```text
Intake → Implementation → Quality Gates → Self-Review → Human Review → Merge → Deploy → Journal
```text

### 1. Intake (человек)

- Задача заведена на доске issue с **критериями приёмки** (acceptance criteria) в теле.
- Критерий готовности задачи к разработке: сформулировано, что должно работать и как проверить.
- Если критерии размыты — агент задаёт вопросы в issue до начала работы.

### 2. Implementation (агент)

- До кодинга — подробный план реализации комментарием в issue: понимание задачи и критериев приёмки, шаги с затрагиваемыми файлами/модулями, подход к тестам. Человек видит намерение агента до появления кода; план остаётся артефактом рядом с критериями.
- Ветка `feature/<N>-<slug>` от свежего `main`.
- Код + тесты на новое поведение (TDD-предпочтение: сначала тест).
- Коммиты по conventional commits (`feat:`, `fix:`, `refactor:`, `test:`, `docs:`).
- PR открывается автоматически из шаблона: что сделано, как проверено, какие критерии закрыты.

### 3. Quality Gates (CI, автоматически)

Обязательные проверки на каждый PR:

- линт / форматирование
- типизация (если применимо)
- тесты
- сборка

Красные проверки = PR не ревьюится и не мёржится. Агент чинит сам.

### 4. Self-Review (агент)

- Агент сам смотрит диф: соответствие критериям приёмки, лишний код, очевидные риски.
- Результат — комментарий в PR: чек-лист критериев с галочками.

### 5. Human Review (человек, минимальное вмешательство)

- Колонка **In Review** на доске = задача ждёт здесь.
- Человек смотрит: диф, результат self-review, зелёные проверки.
- Решения: approve / request changes (с конкретным комментарием) / отклонить.

### 6. Merge (агент по сигналу человека)

- Squash merge в `main`, ветка удаляется.
- Прямые пуши в `main` запрещены (rulesets).

### 7. Deploy (CI/CD)

- Merge триггерит деплой: сборка артефакта → публикация (staging → production по готовности).

### 8. Journal (агент)

- Пост в журнал фабрики: что сделано, сколько вмешательств человека, что пошло не так.

## Метрики фабрики

- **Lead time**: от «In Progress» до «Done»
- **Human touch count**: сколько раз человек вмешивался в задачу (цель → минимум: 1 review)
- **Gate pass rate**: доля PR, прошедших проверки с первого раза
- **Rework rate**: доля задач, вернувшихся из review с правками (цель → стремится к 0)

## Что ещё не решено (вопросы к эволюции)

- Нужен ли staging-контур для G1 или деплой сразу в production
- Кто/что триггерит старт задачи: расписание, команда человека, или агент сам берёт из Todo
- Минимальный набор проверок под конкретный стек G1
