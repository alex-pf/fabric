# Журнал Fabric

Подробная история развития фабрики. Каждая запись: дата, что изменили, какой инструмент внедрили, какую проблему решали, почему приняли именно такое решение. Из этого журнала строится кейс/презентация AI-native процесса.

Формат записей: [ADR-ссылка](decisions/) при наличии, контекст → решение → результат.

---

## 2026-11-23 — Точка старта

**Контекст.** Запускаем портфолио-проект: мета-продукт Fabric (AI-native процесс разработки) + продукт G1 (детская игра), который фабрика будет производить. Ключевой критерий фабрики: продуктовые фичи выпускаются с минимальным вмешательством человека при гарантированном качестве.

**Принятые решения (день 0):**

1. **GitHub как основа CD и хостинга кода.**
   Почему: публичная демонстрация результатов, нативные доски задач (Projects), Actions для CI/CD, привычный стандарт индустрии — читаемость портфолио для рекрутёра/клиента.
   → Репозиторий [`alex-pf/fabric`](https://github.com/alex-pf/fabric), public.

2. **Fabric и G1 — раздельные репозитории.**
   Почему: фабрика — переиспользуемый инструмент, не привязанный к одному продукту. Разделение само по себе демонстрирует ключевую идею: процесс отделён от продукта. Плюс чистое разделение досок, CI и истории.

3. **Две отдельные канбан-доски (GitHub Projects).**
   - Fabric board — задачи по развитию инфраструктуры и процесса.
   - G1 board — продуктовые фичи, техдолг, баги.
   Почему: фабрика и продукт развиваются независимыми потоками; смешение привело бы к приоритетным конфликтам и потере фокуса на мета-продукте (а он — главный артефакт портфолио).

4. **Журнал истории ведём с первого дня, в репозитории (`docs/journal.md`).**
   Почему: эволюция журнала версионируется вместе с кодом; видна не только итоговая методология, но и сам путь — включая ошибки и передумывания. Это и есть материал для будущей презентации.

**Инфраструктурные шаги дня:**
- Авторизация агента (Hermes) в GitHub через OAuth device flow, scope `repo, workflow, read:org, gist, project`. Первый токен был без scope `project` — доска недоступна через API → перевыпуск с расширенным scope. Урок: сразу запрашивать все нужные scope.
- Доска Fabric: [Project #6](https://github.com/users/alex-pf/projects/6) (создана вручную, т.к. Projects API не позволяет создать доску через `gh` без доп. скоупов/приложений).
- Структура репозитория: `docs/`, `pipelines/`, `agents/`.

**Статус:** фабрика заложена. Продукт G1 не начат — обсуждение продукта отложено до готовности базового контура фабрики.

## 2026-11-24 — Доска Fabric и стартовый бэклог

**Контекст.** Репозиторий создан, нужен рабочий процесс: доска + первые задачи, чтобы развитие фабрики шло по канбану, а не хаотично.

**Что сделано:**
- Доска переименована в **Fabric**. Статус-колонки: `Todo → In Progress → In Review → Done`. Колонка **In Review** — осознанное решение: в AI-native процессе есть точка, где человек проверяет работу агента перед принятием; это часть критерия «минимальное вмешательство, но качество».
- Заведены первые 5 задач (issues в репозитории fabric, привязаны к доске):
  1. [Зафиксировать пайплайн разработки фичи](https://github.com/alex-pf/fabric/issues/1) — ядро контура
  2. [CI: линт + тесты + сборка](https://github.com/alex-pf/fabric/issues/2)
  3. [Защита main через rulesets](https://github.com/alex-pf/fabric/issues/3)
  4. [Спайк: агент ведёт задачу до PR end-to-end](https://github.com/alex-pf/fabric/issues/4)
  5. [Создать репозиторий и доску G1](https://github.com/alex-pf/fabric/issues/5)
- Порядок осознанный: сначала процесс/качество (1–3), потом доказательство end-to-end (4), потом запуск продукта (5).

**Урок дня:** GitHub Projects API не умеет создавать доску (только через web/UI), но полностью умеет ею управлять (переименование, колонки, привязка issues) — достаточно scope `project`.

## 2026-11-24 — Пайплайн разработки фичи

**Контекст.** Задача #1 с доски: до этого фабрика была набором решений, нужно было ядро — стандартный контур доставки, куда встраиваются все будущие улучшения.

**Что сделано:** написан и зафиксирован [`docs/pipeline.md`](../pipeline.md) — 8 этапов: Intake → Implementation → Quality Gates → Self-Review → Human Review → Merge → Deploy → Journal. Ключевые решения внутри:

- **Quality Gates как гарант качества:** линт/типы/тесты/сборка обязательны на каждый PR, красные проверки не ревьюятся. Качество обеспечивается воротами, а не review человека.
- **Human Review — единственная обязательная точка человека.** Это и есть «минимальное вмешательство»: человек принимает решение (approve/request changes), а не пишет код.
- **Self-Review агента до review человека:** агент сам проверяет диф по критериям приёмки и приносит чек-лист — уменьшает число возвратов.
- **Метрики фабрики** зафиксированы: lead time, human touch count, gate pass rate, rework rate. Без метрик нельзя доказать «минимальное вмешательство».

**Честная заметка для истории:** сам документ закоммичен напрямую в main, минуя PR — пайплайн формально ещё не существовал на момент коммита. Со следующего изменения фабрика работает по своим же правилам: ветка → PR → проверки → review. Фабрика применяет к себе свои правила — это принцип, не рекомендация.
